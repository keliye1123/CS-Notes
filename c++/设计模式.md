## 单例模式
- 私有化构造函数。删除拷贝构造和赋值：防止外部创建和赋值实例。
- 静态成员变量：保存唯一实例。
- 静态成员访问方法：获取唯一实例。

### 懒汉模式
只有在创建的时候创建全局单例，没用到时不创建。
- 例子：
~~~ cpp
class Game {
 //方法
private:
    Game() = default;//私有化构造函数

public:
    Game(const Game&) = delete;//删除拷贝构造
    Game& operator=(const Game&) = delete;//删除赋值
    static Game& getInstance(){//c++11后推荐的单例实现，在创建时线程安全
        static Game game;
        return game;
    }
}
~~~

### 饿汉模式
在使用前就直接创建了。

### 单例模式的优缺点
- 优点：全局访问十分方便
- 缺点：想要使用Game单例，则需要include<game.h>这个头文件，增加了项目的耦合度。


## 组合模式
一种结构型设计模式，将对象看做一个树状结构，其有一个容器存储子节点将他的总功能分为一个个子节点小的功能，子节点功能又分为一个子节点更小的功能。
且这些子节点能够拆分和添加，耦合度低。

## 职责链
一种行为设计模式，允许你
将请求沿着处理者链进行发
送。收到请求后，每个处理
者均可对请求进行处理，或
将其传递给链上的下个处理
者。

- 例子：在handleEvent中Event变量层层传递当遇到处理者时返回true结束传递。

## 模板方法模式
一种行为设计模式，它在超
类中定义了一个算法的框架，
允许子类在不修改结构的情
况下重写算法的特定步骤。

- 例子：在游戏设计中，一个超类Game有个run函数，在主循环中按顺序循环执行init，handleEvent，update，render，clean，整个程序按照这个模版进行
~~~cpp
void Game::run() {
    while (isRunning_) {
        auto start = SDL_GetTicksNS();
        if (nextScene_) {
            currentScene_ -> clean();
            delete currentScene_;
            currentScene_ = nextScene_;
            nextScene_ = nullptr;
            currentScene_ -> init();
        }
        handleEvents();
        update(deltaTime_);
        render();

        auto end = SDL_GetTicksNS();
        auto elapsed = end - start;
        if (elapsed < frameTime_) {
            SDL_DelayNS(frameTime_ - elapsed);
            deltaTime_ = frameTime_ / 1.0e9;
        }
        else {
            deltaTime_ = elapsed / 1.0e9;
        }

    }
}
~~~

## 原型模式
一种创建型设计模式，使你
能够复制已有对象，而又无
需使代码依赖它们所属的类。

- 缺点：需要在类中保存对象，如果对象很大会很浪费内存，所以并不常用，一般用工厂方法模式替代。


## 工厂方法模式
一种创建型设计模式，
其在父类中提供一个创
建对象的方法，允许
子类决定实例化对象的
类型。

- 优点：相对于原型模式，不需要再类内保存对象，只需要在类内保存一个简单的创建对象类的父类，根据需求传入创建对象类的子类，设计不同的子类创建不同的对象。

## 状态模式
一种行为设计模式，让你能
在一个对象的内部状态变化
时改变其行为，使其看上去
就像改变了自身所属的类一
样。

- 在类内创建一个保存一个状态成员基类，在通过修改函数来切换不同的子类状态

## 对象池模式
在创建很多对象时，我们可以不单独new对象，而是设计一个存储对象的对象池类，初始存入多个对象，对象可以以链表方式链接，需要时取出，用完时放回，可以用空间换时间。

## SOLID原则
- S单一职责原则：一个类应该只有一个引起它变化的原因（一个类应该只负责一个功能或任务）
- O开闭原则：软件实体应该是可扩展的，但是不可修改的。 (我们应该在不修改现有代码的情况下添加新的功能)
- L里氏替换原则：子类型必须能够替换掉它们的基类型。
- I接口隔离原则：客户端不应该被强迫依赖它们不使用的接口。
- D依赖倒置原则：1.高层模块不应该依赖于低层模块。两者都应该依赖于抽象 2.抽象不应该依赖于细节。细节应该依赖于抽象。
  （高层的对象与底层的模块要以抽象接口作为连接而不直接连接，细节具体实现应根据抽象接口来修改自身而不是去修改接口）
